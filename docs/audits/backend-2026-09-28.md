# Backend audit — 2026-09-28

This is a historical evidence snapshot for the backend implementation of M01–M12 and M14–M15. The audited source, tests, and deployment files were removed on 2026-09-28. Paths below identify files as they existed during the audit; they are no longer links to current code. Each ticket remains authoritative for its current triage and completion state. M16 requires site hardware and is outside this audit.

## Verification performed

- `PYTHONPATH=src .venv/bin/python -m unittest discover -s tests -p 'test_*.py'`: 55 tests passed with Python 3.14.4 after installing `requirements.txt` in the local `.venv`.
- `docker compose config --quiet` and `docker compose build ingestion`: both passed; the built image uses Python 3.11.
- Isolated reproductions used temporary SQLite files, mock adapters, a stub MQTT client, and Flask's test client. They did not contact a real dispenser, broker, PostgreSQL, or InfluxDB service.

The passing suite does not demonstrate full ticket acceptance. The single end-to-end test disables destinations and waits only three seconds before checking data, while its inventory interval is ten seconds (`tests/integration/test_end_to_end.py`).

## Confirmed findings

### B01 — Model II first physical read deadlocks (high; M05)

`execute_upload_command()` holds a non-reentrant lock, then calls `connect()` when disconnected; `connect()` tries to acquire the same lock (`src/musashi_ingestion/devices/model_ii/adapter.py`). With a stub serial port, the first `upload_data("D06")` thread remained blocked. Mock adapter tests do not exercise this path. A physical Model II worker cannot complete its first read through this adapter.

### B02 — Management API permits unauthenticated control with default configuration (high; M04, M14)

An empty `OPERATOR_TOKEN` makes `check_auth()` return true. Both `.env.example` and `compose.yml` default to an empty value, and Compose publishes the API port on the host. A Flask test client received HTTP 200 from `POST /api/control/start` without credentials. Even with a token configured, `GET /api/config` and `GET /api/status` have no authentication check (`src/musashi_ingestion/api/app.py`).

### B03 — Spool limits are checked after the fact, and a full spool kills a worker (high; M07–M09)

`commit_record()` checks current file size before insertion and writes the payload without invoking the record's 10 MB serialization check (`src/musashi_ingestion/pipeline/spool.py`, `src/musashi_ingestion/pipeline/record.py`). A 2 MB record was accepted with a 1 MB spool limit. With the record-count limit reached, a mock worker's error handler attempted to commit an event, raised `SpoolFullError`, and its thread exited; `get_status()` still reported `running: true` (`src/musashi_ingestion/runtime/machine_worker.py`). This defeats the ticket's stop-and-visible-fault policy.

### B04 — Changing a destination reuses its identity (high; M09)

The supervisor uses fixed IDs such as `mqtt_primary`; `register_destination()` updates the hash in place under that ID (`src/musashi_ingestion/runtime/supervisor.py`, `src/musashi_ingestion/pipeline/spool.py`). A pending record assigned under the old hash remained pending under the same ID after changing the hash. The new worker would read that old record, so the implementation does not preserve the old target's delivery identity.

### B05 — Model IV inventory can miss data and stays partial in mock mode (high; M06, M08)

The `/data/all` branches set success after iterating whatever items are returned; they do not check expected IDs or fill gaps through individual requests. The sweep also omits the recipe and channel `/range` endpoints and does not count machine/time reads as inventory items (`src/musashi_ingestion/runtime/machine_worker.py`). Running the complete IV mock sweep produced `partial`, with 17 completed items out of 511 expected. Missing items have no individual failure entry when `/data/all` returns a subset.

### B06 — InfluxDB conversion drops nested values and allows point collisions (high; M12)

`record_to_line_protocol()` emits only top-level scalar payload fields. Nested portions of status, common settings, exports, and logs are omitted, yet a successful HTTP write acknowledges the source record (`src/musashi_ingestion/destinations/influx_worker.py`). Two records with different IDs but the same machine, type, quality, and observed timestamp generated the same measurement, tag set, and timestamp; `record_id` is only a field. The required distinct-record identity has not been established.

### B07 — MQTT chunks can exceed the configured byte limit (medium; M10)

Chunking slices the Unicode JSON string by character count and assumes a fixed 512-byte envelope overhead (`src/musashi_ingestion/destinations/mqtt_worker.py`). With `max_payload_bytes=1024` and a non-ASCII payload, a stub client received a 3,179-byte chunk, after which the record was acknowledged. The per-message limit is therefore not enforced.

### B08 — The first inventory waits for the refresh interval (medium; M08)

The run loop initializes `last_inventory_time` to the current monotonic time, then starts a sweep only when the configured interval elapses (`src/musashi_ingestion/runtime/machine_worker.py`). The default interval is one hour (`src/musashi_ingestion/config/models.py`). This conflicts with M08's requirement to run an inventory at startup and leaves new installations without inventory coverage until that delay passes.

### B09 — PostgreSQL has no inventory completion model (medium; M11)

The destination migration creates only `musashi_records`; it does not persist scan status or item coverage (`src/musashi_ingestion/destinations/postgres_worker.py`). The ticket requires consumers to distinguish complete from partial inventories using PostgreSQL queries. There was no PostgreSQL integration test or example query in the audited checkout.

### B10 — End-to-end qualification does not cover delivery or inventory (medium; M15)

The only integration scenario enables no destination, waits three seconds before checking records, and configures a ten-second inventory interval (`tests/integration/test_end_to_end.py`). It verifies status and a simulated II failure, but does not exercise MQTT, PostgreSQL, InfluxDB, inventory coverage, large payloads, or the failure matrix required by M15.

## Rebuild considerations

The findings describe the removed implementation, not current defects in a running service. Address these failure modes when rebuilding M03–M15, then verify destination behavior against test services and run the M15 scenario matrix. Hardware protocol claims remain pending M16.
