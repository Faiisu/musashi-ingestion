# Agent execution contract for M17–M33

This page fixes shared input and output shapes for the implementation tickets. Each ticket names its own work, cases, and evidence. The [source-of-truth map](../ssot.md) still distinguishes intended behavior here from current behavior in code. A passing synthetic case is never hardware evidence.

## Common handoff rules

1. Start only after the ticket's `Depends on` work has `Completion: verified`, or record the specific dependency as a blocker. M18 and M19 have no implementation prerequisite. M33 additionally requires site access and an operator.
2. Read the named source files, make the smallest owning-module change, and update the named ticket's acceptance evidence. Keep `Status:` and `Completion:` unchanged until every listed check has evidence. When a required environment or external input is absent, report `blocked` with its missing input and do not substitute a synthetic success.
3. Deliver a change list, commands and exact results of required checks, a table mapping every acceptance case to an evidence path, and remaining blockers. For code tickets, run `uv run python -m unittest discover -s tests -v` after adding the named cases; the ticket's disposable-service or site procedure is an additional gate. A failure is a failed case, not a skipped case. New tests belong in the existing `tests/` layout and use synthetic fixtures unless the ticket explicitly requires a disposable service or named site device.
4. Preserve the separation in [ADR 0002](../adr/0002-independent-collection-and-destination-rerouting.md): device collectors produce records and scan outcomes; the spool validates, persists, retains, and assigns them; each forwarder consumes only its own pending assignments and reports remote confirmation. A destination does not call a device adapter, and a collector does not call a destination.

## Shared data shapes

- An observation is version 1 JSON with `record_id` (stable UUID string), `machine_id`, `model` (`II` or `IV`), `record_type` (`status`, `inventory`, `scan`, or `error`), `source`, `observed_at` (UTC RFC 3339), `channel_id` (integer or null), `values` (object), and `evidence_type` (`simulated`, `documented`, or `hardware-verified`). The collector puts parsed data in `values.value`, safe raw data in `values.raw`, scope in `values.scope`, and quality in `values.quality` (`good`, `unavailable`, `incomplete`, `partial`, or `error`). The spool adds immutable `installation_id` and `point_time_ns` under [ADR 0001](../adr/0001-influx-point-identity.md). A failed read may produce an `error` record but never a successful observation or a reused prior value. No forwarder changes this body.
- An inventory item key is `Dxx:<channel>` for II or the exact allowlisted path for IV. Expected item keys are persisted when a scan starts. An outcome is `ok` with a record ID, `unsupported` with an optional record ID, or `failed` with no successful observation. A missing outcome is displayed as missing/skipped. `completed_at` is set only when the expected set is nonempty and every item is `ok` or `unsupported`; otherwise the scan is partial. Scan delivery is a version 1 `record_type: "scan"` envelope whose `values.value` is the full scan snapshot, including expected items and outcomes. Send a partial snapshot when a scan stops or fails; send a complete snapshot when it finishes. Use the same scan ID for snapshots of one scan.
- An explicit device rejection maps to `unsupported`. JSON `null` is a successful read with `values.value: null` and `quality: "unavailable"`; malformed data, transport errors, timeout, redirect, and over-limit data map to failure. The fault identifies machine and source. Never reuse a prior value.
- A destination lane is the stable configured `destinations[].id`. Endpoint identity is a revision of that lane's connection settings and secret content. A delivery row is pending until remote confirmation, then acknowledged. Initial registration assigns only retained records to that lane in commit order. Endpoint change is applied while acquisition and forwarders are stopped: create the new endpoint identity, reassign that lane's pending rows in one SQLite transaction, leave acknowledged rows and other lane IDs untouched, and store counts and the old/new endpoint identities in a reroute audit row. An uncertain old acknowledgment may cause the same `record_id` at both endpoints.
- Retention is a configurable count `retention_max_history_records`, default 100, integer 0 or greater. On a quota-pressure prune, delete the oldest unassigned or fully acknowledged records beyond the most recent count, including only completed scan history no longer referenced by retained records. Pending assignments and incomplete scans are protected. Expose oldest retained `committed_at` and a monotonically increasing pruned-record count; a new destination can backfill only records still present. If protected bytes still exceed quota, fail the write and set acquisition fault. These numbers are software policy; M33 measures site adequacy.

## Limits and error behavior

- Unless a ticket gives a narrower limit: whole device request deadline 2 seconds; raw device response and serialized record maximum 2,097,152 bytes each; spool allocation 1,073,741,824 bytes including SQLite files and WAL; MQTT encoded message maximum 262,144 bytes including its chunk envelope. Decode or size rejection does not create a successful observation or acknowledge a delivery.
- The status API must expose machine/source faults, pending count and oldest pending age by lane, scan state and missing item keys, retained-history boundary and prune count, current disk/WAL bytes, acquisition fault, and worker liveness. `GET /health` remains non-sensitive; topology and record/scan/status reads require a nonempty bearer token. An error response never includes secret content.
- A disposable service test must record the exact source fixture ID and original record ID, remote query or received payload, equality result for the complete JSON body, spool pending/ack state, and fault/retry outcome. For all three destinations, compare the same complete record family set: II `D01`–`D09`, IV 16 status paths, IV machine/time, common data/ranges, recipe/channel all/ranges/per-ID fallback, export data/log, diagnostic results, and complete and partial scan snapshots. The fixture matrix may synthesize minimal bodies for each family; its manifest must enumerate each family and expected result.

## Minimal example

The collector input below is a synthetic example. The spool adds the two point-identity fields before persistence and forwarding.

```json
{"version":1,"record_id":"00000000-0000-4000-8000-000000000001","machine_id":"ii-1","model":"II","record_type":"status","source":"D01","observed_at":"2026-09-28T00:00:00Z","channel_id":1,"values":{"value":{"pressure_kpa":98.7},"raw":"0240...03","scope":"channel","quality":"good"},"evidence_type":"simulated"}
```

For a two-item scan, expected keys are `D01:1` and `D02:1`. A successful first item and explicitly unsupported second item produce `items: [{"item_key":"D01:1","record_id":"<record UUID>","outcome":"ok"},{"item_key":"D02:1","record_id":null,"outcome":"unsupported"}]` and non-null `completed_at`. If the second outcome is `failed` or null, `completed_at` stays null and the snapshot state is `partial`.
